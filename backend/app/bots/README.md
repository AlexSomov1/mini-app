Полное ТЗ к боту:
"""
✅ BOTS FOLDER: ПОЛНОЕ ТЗ ДЛЯ ПАПКИ bots/
==================================================
bots/ — весь код Telegram-бота проекта mini-app

🎯 ГЛАВНАЯ ЦЕЛЬ ПАПКИ
--------------------------------------------------
Папка bots/ отвечает за Telegram-бота как за отдельный прикладной слой проекта.

Этот слой должен:
- принимать входящие сообщения, команды и callback query из Telegram;
- показывать пользователю меню и кнопки;
- запускать сценарии взаимодействия;
- уведомлять студентов и кураторов о событиях;
- связывать Telegram-пользователя с backend-сущностями проекта;
- вызывать backend/service-логику;
- не хранить у себя тяжелую бизнес-логику домена.

Главная идея:
bots/ — это не место, где заново реализуются users_service, themes_service,
requests_service и admin_service.

Правильная архитектура:
Telegram update → bot handler/router → bot service / api client → backend service/API

или, если монолит:
Telegram update → bot handler/router → app.services.* → db

Бот должен быть "тонким" интерфейсным слоем,
а не второй независимой бизнес-системой.

--------------------------------------------------
📦 ОБЩАЯ ЗОНА ОТВЕТСТВЕННОСТИ ПАПКИ bots/
--------------------------------------------------
Папка bots/ отвечает за:

1. Инициализацию Telegram-бота
   - Bot
   - Dispatcher
   - start polling / webhook startup
   - регистрация router-ов

2. Обработку Telegram update-ов
   - /start
   - /help
   - callback_query
   - inline/reply keyboard interactions
   - FSM / пошаговые сценарии

3. Пользовательские сценарии
   - запуск бота
   - просмотр меню
   - переход в mini app / webapp
   - просмотр своих тем или заявок
   - получение уведомлений по заявкам и темам

4. Сервисные сценарии
   - уведомление о создании темы
   - уведомление о новой заявке creator-у
   - уведомление пользователю об approve/reject
   - broadcast от админа

5. Админские/кураторские сценарии
   - команды модерации
   - массовая рассылка
   - служебные меню
   - получение статистики, если это предусмотрено

6. Интеграцию с backend
   - вызов API
   - либо вызов app.services в монолите
   - преобразование данных backend → telegram message format

7. Вспомогательные компоненты бота
   - keyboards
   - filters
   - middlewares
   - formatters
   - bot-specific services
   - константы текстов

--------------------------------------------------
🚫 ЧЕГО В ПАПКЕ bots/ БЫТЬ НЕ ДОЛЖНО
--------------------------------------------------
В папке bots/ не должно быть:

- прямой доменной бизнес-логики users/themes/requests/admin,
  если эта логика уже существует в app/services;

- сложных SQL-запросов к таблицам,
  если проект уже использует service/repository слой;

- дублирования API-логики из FastAPI роутеров;

- хранения всех текстов, клавиатур, фильтров и handlers в одном огромном файле;

- хардкода токена бота, ADMIN_IDS, URL backend, chat_id и других секретов;

- циклических импортов между bot handlers и api modules;

- ручного "if text == ..." вместо нормальных router/filter подходов;

- смешивания FSM-логики, Telegram UI, HTTP-запросов и SQL в одном handler-е.

Если бот внутри одного handler делает:
- SQL,
- отправку 7 разных сообщений,
- проверку admin,
- бизнес-валидацию,
- вызов внешнего API,
- ручной парсинг callback_data,
значит архитектура перегружена и код нужно разносить по слоям.

--------------------------------------------------
📄 НАЗНАЧЕНИЕ КЛЮЧЕВЫХ ФАЙЛОВ
--------------------------------------------------

1. bots/main.py
----------------
Главная точка входа Telegram-бота.

Файл должен:
- создать Bot и Dispatcher;
- подключить config/settings;
- подключить routers;
- зарегистрировать middlewares;
- запустить polling или webhook;
- корректно закрыть bot session при завершении.

Этот файл не должен:
- содержать handlers;
- содержать тексты сообщений;
- содержать бизнес-логику;
- содержать клавиатуры;
- содержать SQL.

Главная задача main.py:
инициализация и запуск.

2. bots/config.py
-----------------
Конфигурация бота.

Здесь должны храниться:
- BOT_TOKEN
- BOT_PARSE_MODE
- ADMIN_IDS или BOT_ADMIN_IDS
- WEBAPP_URL
- BACKEND_URL
- ENV
- LOG_LEVEL
- USE_WEBHOOK / USE_POLLING
- WEBHOOK_SECRET (если нужен)

Файл должен брать значения из env/settings,
а не хардкодить их.

Если в проекте уже есть единый settings в app.core.config,
лучше не дублировать config, а импортировать общий settings.

3. bots/loader.py
-----------------
Опциональный файл для централизованной сборки bot, dp, routers, services.

Нужен, если хочешь отделить запуск от создания объектов.

Он может:
- собирать Dispatcher;
- регистрировать routers;
- возвращать bot, dp.

4. bots/routers/...
-------------------
Router-файлы aiogram.

Каждый router должен отвечать за одну группу сценариев:
- start.py → /start, /help
- menu.py → главное меню
- themes.py → действия, связанные с темами
- requests.py → действия, связанные с заявками
- admin.py → админ-команды и admin callbacks
- fallback.py → неизвестные команды/сообщения

Каждый router должен быть маленьким и тематическим.

5. bots/handlers/...
--------------------
Если проект разделяет router и handlers отдельно,
то handlers содержат сами функции обработки update-ов,
а routers лишь регистрируют их.

Если разделение кажется избыточным,
можно держать только routers/, но тогда не делать один огромный файл.

6. bots/keyboards/...
---------------------
Все inline/reply клавиатуры бота.

Нужно вынести:
- стартовое меню;
- кнопки "Открыть mini app";
- кнопки approve/reject;
- админские кнопки;
- кнопки навигации назад/в меню;
- keyboard builders для динамических списков.

В handler-ах не должно быть 20 строк InlineKeyboardButton подряд.
Клавиатуры должны собираться в отдельном модуле.

7. bots/middlewares/...
-----------------------
Промежуточные слои aiogram.

Возможные задачи:
- логирование update-ов;
- проброс db/session/context;
- ограничение частоты сообщений;
- автоматическая загрузка user context;
- единая обработка ошибок.

8. bots/filters/...
-------------------
Кастомные фильтры для aiogram.

Примеры:
- IsAdmin
- PrivateChatOnly
- IsRegisteredUser
- HasWebAppAccess

Это позволяет не писать в каждом handler-е ручные if-проверки.

9. bots/states/...
------------------
FSM-состояния для пошаговых сценариев.

Примеры:
- рассылка админа;
- создание темы через бота;
- подтверждение модерации;
- форма обратной связи.

Если сценариев нет, states/ может быть почти пустой,
но папка должна быть предусмотрена архитектурно.

10. bots/services/...
---------------------
Bot-specific сервисы.

Это НЕ основной domain service слой проекта.
Это сервисы, которые нужны именно боту:

- api_client.py
  обертка над backend API;
- notifications.py
  отправка уведомлений пользователям;
- messages.py
  высокоуровневые функции отправки сообщений;
- deeplinks.py
  генерация deep link URL;
- formatter.py
  форматирование текста для Telegram.

Здесь не должно быть повторной реализации users_service/themes_service.
Здесь должно быть:
"как боту удобно общаться с backend и Telegram".

11. bots/utils/...
------------------
Мелкие вспомогательные функции:
- безопасная отправка сообщений;
- форматирование дат;
- callback_data helpers;
- ссылки;
- текстовые экранирования.

12. bots/texts/...
------------------
Все тексты сообщений бота.

Важно:
тексты должны быть вынесены из handlers.
Не надо держать длинные многострочные message templates прямо в коде роутеров.

Примеры:
- приветствие
- help
- текст уведомления об approve
- текст уведомления об отклонении
- текст админской рассылки
- текст ошибок

13. bots/README.md
------------------
Документация по папке bots/.

В README должно быть:
- как запустить бота;
- какие env нужны;
- как он связан с backend;
- какие основные сценарии поддерживаются;
- где лежат handlers/keyboards/texts;
- как добавить новый handler.

--------------------------------------------------
🤖 ОСНОВНЫЕ СЦЕНАРИИ, КОТОРЫЕ ДОЛЖЕН ПОДДЕРЖИВАТЬ БОТ
--------------------------------------------------

1. /start
---------
После команды /start бот должен:
- приветствовать пользователя;
- объяснять, что это за проект;
- давать кнопку для открытия mini app;
- при необходимости регистрировать/синхронизировать Telegram пользователя;
- показывать базовое меню.

Если проект использует Telegram WebApp,
то /start должен в первую очередь вести пользователя в web app,
а не пытаться реализовать весь интерфейс только сообщениями.

2. Главное меню
---------------
Бот должен давать пользователю понятную точку входа:
- открыть mini app;
- мои темы;
- мои заявки;
- помощь;
- связь с куратором / правила.

3. Уведомление о новой заявке
-----------------------------
Когда кто-то подал заявку на тему,
бот должен уметь уведомить создателя темы.

Пример:
- название темы;
- кто подал заявку;
- когда подал;
- кнопки approve/reject или ссылка в mini app.

4. Уведомление об approve/reject
--------------------------------
Когда creator или модератор обработал заявку,
бот должен отправить пользователю уведомление:

- заявка одобрена;
- заявка отклонена;
- тема;
- дата/место;
- возможная ссылка на детали.

5. Админская рассылка
---------------------
Куратор должен иметь возможность отправить broadcast:
- всем;
- активным;
- выбранной группе (если потребуется потом).

6. Служебные ошибки и fallback
------------------------------
Бот должен корректно отвечать:
- на неизвестную команду;
- на невалидный callback;
- на устаревшую кнопку;
- на внутреннюю ошибку.

Нельзя оставлять пользователя без ответа.

--------------------------------------------------
🔗 ИНТЕГРАЦИЯ С BACKEND
--------------------------------------------------
Папка bots/ должна быть четко согласована с backend-слоем.

Есть 2 допустимые модели:

Модель A: бот вызывает backend API
----------------------------------
Бот работает как отдельный клиент:
- делает HTTP-запросы в FastAPI;
- получает JSON;
- форматирует сообщение в Telegram.

Плюсы:
- хорошее разделение;
- удобно отделять bot и backend;
- ближе к реальной production архитектуре.

Минусы:
- нужно поддерживать API client;
- больше сетевых вызовов.

Модель B: бот внутри одного монолита вызывает app.services
----------------------------------------------------------
Если bot и backend в одном коде,
бот может обращаться к app.services напрямую.

Плюсы:
- проще на ранней стадии;
- меньше прослоек.

Минусы:
- выше связанность;
- надо аккуратно следить, чтобы handlers не полезли в SQL напрямую.

Важно:
независимо от модели,
bot handlers не должны писать бизнес-логику домена сами.

--------------------------------------------------
🔐 АВТОРИЗАЦИЯ И ИДЕНТИФИКАЦИЯ ПОЛЬЗОВАТЕЛЯ
--------------------------------------------------
Папка bots/ должна работать с Telegram user как с первичным источником identity.

Бот должен уметь получать:
- telegram_id
- username
- first_name
- last_name
- chat_id

Но при этом:
- проверка прав admin должна быть централизована;
- бан-статус должен браться из backend/service;
- бот не должен сам хранить вторую отдельную систему ролей.

Если пользователь забанен:
- бот должен корректно сообщать об ограничении;
- либо вообще ограничивать сценарии кроме базовой информации.

--------------------------------------------------
🔔 УВЕДОМЛЕНИЯ
--------------------------------------------------
Папка bots/ обязана поддерживать систему уведомлений.

Минимальные уведомления:
1. Новая заявка создателю темы.
2. Approve заявки пользователю.
3. Reject заявки пользователю.
4. Broadcast от админа.

Желательно предусмотреть высокоуровневый сервис:

bots/services/notifications.py

Он должен содержать функции вроде:
- notify_new_request(...)
- notify_request_approved(...)
- notify_request_rejected(...)
- notify_broadcast(...)

Тогда остальной код проекта не будет знать,
как именно формируется Telegram-сообщение.

--------------------------------------------------
🧠 FSM / СОСТОЯНИЯ
--------------------------------------------------
Если в боте есть многошаговые сценарии,
они должны быть реализованы через FSM.

Примеры сценариев:
- админ вводит текст рассылки;
- бот просит подтвердить отправку;
- админ подтверждает;
- бот запускает отправку.

Другой пример:
- создание темы через бота;
- шаг 1: название;
- шаг 2: дата и время;
- шаг 3: место;
- шаг 4: подтверждение.

FSM должен быть изолирован в states/ и handlers,
а не размазан по разным файлам через if/else.

--------------------------------------------------
⌨️ КЛАВИАТУРЫ
--------------------------------------------------
Клавиатуры Telegram должны быть вынесены в отдельные модули.

Типы клавиатур:
- reply keyboard для базовой навигации;
- inline keyboard для действий;
- web app button для открытия mini app;
- admin inline keyboard для модерации.

Каждая клавиатура должна:
- иметь понятное имя;
- быть переиспользуемой;
- не собираться вручную в каждом handler-е;
- использовать callback_data с предсказуемым форматом.

--------------------------------------------------
🏷 CALLBACK DATA
--------------------------------------------------
Все callback_data должны иметь единый формат.

Пример:
- req:approve:15
- req:reject:15
- theme:open:3
- admin:broadcast:confirm

Лучше использовать aiogram CallbackData factory или собственный helper.

Важно:
- callback_data не должна собираться хаотично строками по всему проекту;
- формат должен быть централизован;
- обработка должна быть устойчива к битым/устаревшим callback.

--------------------------------------------------
📝 ТЕКСТЫ И ФОРМАТИРОВАНИЕ
--------------------------------------------------
Тексты сообщений должны быть централизованы.

Не надо делать так:
@router.message(...)
async def handler(...):
    await message.answer("Привет! Это очень длинный текст на 12 строк ...")

Нужно выносить тексты в texts/* и formatter/service слой.

Форматирование должно учитывать:
- ParseMode (HTML или MarkdownV2);
- экранирование спецсимволов;
- переносы строк;
- читаемость в Telegram.

Желательно иметь formatter.py для:
- карточки темы;
- карточки заявки;
- текста статистики;
- текста уведомления.

--------------------------------------------------
🧯 ОБРАБОТКА ОШИБОК
--------------------------------------------------
В папке bots/ должна быть единая стратегия ошибок.

Нужно обработать:
- backend недоступен;
- Telegram API error;
- user blocked bot;
- invalid callback data;
- missing entity;
- forbidden action;
- timeout.

Желательно:
- логировать ошибку;
- показывать пользователю дружелюбное сообщение;
- не падать всем polling-процессом из-за одной ошибки.

Для этого может быть middleware или общий error handler.

--------------------------------------------------
📊 ЛОГИРОВАНИЕ
--------------------------------------------------
Бот должен логировать:
- запуск/остановку;
- входящие команды;
- критические действия (approve/reject, broadcast);
- ошибки Telegram API;
- ошибки backend интеграции.

Но нельзя логировать:
- bot token;
- секреты;
- чувствительные персональные данные без необходимости.

--------------------------------------------------
🧪 ТЕСТИРОВАНИЕ ПАПКИ bots/
--------------------------------------------------
Минимально должны быть протестированы:

1. /start
   - бот отвечает приветствием
   - есть кнопка web app/menu

2. Админский доступ
   - admin проходит
   - non-admin получает отказ

3. Уведомление approve
   - формируется корректный текст
   - отправка вызывается нужной функции

4. Callback approve/reject
   - callback корректно разбирается
   - вызывается нужный service

5. Broadcast FSM
   - ввод текста
   - подтверждение
   - отправка

6. Fallback
   - неизвестная команда не ломает бота

Если полноценные интеграционные тесты сложны,
минимум должны быть unit-тесты formatter-ов,
callback parsing и bot service функций.

--------------------------------------------------
💡 MVP vs PRODUCTION
--------------------------------------------------

MVP минимум:
- запуск бота через polling;
- /start;
- кнопка открытия mini app;
- уведомление о новой заявке;
- уведомление approve/reject;
- admin broadcast;
- базовые keyboards;
- базовые texts;
- простая структура handlers/services.

Production:
- webhook;
- retry/backoff;
- централизованный error handler;
- FSM сценарии;
- аудит админских действий;
- rich formatting;
- throttling;
- metrics/monitoring;
- полноценный notification service;
- автотесты.

--------------------------------------------------
✅ КРИТЕРИИ ГОТОВНОСТИ ПАПКИ bots/
--------------------------------------------------
Папка bots/ считается спроектированной правильно только если:

1. В ней есть четкая точка входа бота.
2. Логика разбита на handlers/routers, keyboards, services, texts, states.
3. В handlers нет тяжелой бизнес-логики и SQL.
4. Все Telegram уведомления вынесены в отдельный notifications/service слой.
5. Клавиатуры вынесены в отдельные модули.
6. Тексты вынесены из handler-ов.
7. Callback data имеет единый формат.
8. Админские проверки централизованы.
9. Интеграция с backend оформлена отдельным слоем, а не хаотичными вызовами.
10. Ошибки логируются и не валят весь бот.
11. Структура масштабируется под новые сценарии.
12. Папка не дублирует backend domain logic.

--------------------------------------------------
✅ ГЛАВНАЯ МЫСЛЬ
--------------------------------------------------
Папка bots/ должна быть полноценным Telegram-интерфейсным слоем проекта:
аккуратно структурированным, расширяемым и изолированным от доменной логики.

Это не просто "файл с командами бота",
а отдельная подсистема со своими:
- handlers,
- keyboards,
- states,
- notification services,
- formatters,
- texts,
- admin сценариями,
- интеграцией с backend.

Правильный bots/ — это слой общения с пользователем через Telegram,
а не место, где вручную переписывается вся логика backend.
